02 / DEFINE THE QUESTION · 口径与 SQL

这一步做的是业务口径筛选，不是通用清洗

本案例保留有客户 ID、数量与单价为正、且发票号不以 C 开头的交易明细，用于构建本次定义的“有效销售明细”。它服务于特定分析目标，不是所有电商分析都应套用的清洗标准（例如研究退货行为时，取消单恰恰是核心样本）。此外，SQL 中没有使用 DISTINCT，也没有调用 drop_duplicates。

DUCKDB / SQL（实际口径摘要 · ds1 为原始数据集视图别名）
SELECT
  "InvoiceNo",
  CAST(CAST("CustomerID" AS BIGINT) AS VARCHAR) AS "CustomerID",
  "InvoiceDate", "Quantity", "Price", "Country",
  ROUND("Quantity" * "Price", 2) AS "Amount"
FROM ds1
WHERE "CustomerID" IS NOT NULL
  AND "Quantity" > 0
  AND "InvoiceNo" NOT LIKE 'C%'
  AND "Price" > 0;
03 / THE MISSING CONTEXT · 字段集合变化

少了商品信息，“完全重复行”有了新的含义

规则引擎的“完全重复行”检查比较的是当前输出表的全部列。原始数据有 8 列，筛选输出移除了 StockCode 与 Description 并派生了 Amount（8 列变为 7 列）。原先由商品码或商品说明区分的两条明细，投影到更少字段后，就可能在全部输出列上变得完全相同；新增的 Amount 由数量与单价计算，不会补回商品身份。

字段映射：8 列 → 7 列

InvoiceNo StockCode（移除） Description（移除） Quantity InvoiceDate Price CustomerID（转整型再转字符串） Country + Amount（派生）

04 / READ BEFORE YOU REPAIR · 从评分回到判断

先解释口径，再决定是否去重

体检引擎的价值是让异常浮出水面，而不能替代分析判断。仅凭聚合结果不足以断言 314,891 条相同行全部合法或全部该删；正确的下一步是沿着原始记录确认三件事：

01

分析单位是什么？

一笔订单、一条商品明细，还是一位客户？先明确输出表的一行代表什么，再谈重复。

02

判重需要哪些字段？

回到原始商品字段，确认当前保留列是否足以区分不同明细，而非只盯输出表总分。

03

相同行怎样产生？

投影碰撞、重复导入还是业务拆分？需要记录级证据核实后，再决定保留、合并或删除。

05 / TRACE THE EVIDENCE · 来源、署名与局限

让每个数字都有可以回去的地方

本案例局限与非声明
  • 前后缺失单元格、重复数与总分不来自完全相同的行列集合，不能单独用来证明整体数据质量改善或退步。
  • 不是本轮性能测试，不声明所有百万行数据都能秒级处理；不是用户使用统计，不声明节省时间、商业收益或准确率提升。
  • 质量评分及扣分项为当时规则引擎输出；存储扣分项存在舍入，不用于精确重算总分。
