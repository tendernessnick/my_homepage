02 / DEFINE THE QUESTION先定分析口径

这一步做的是筛选，
没有执行去重。

本案例选择有客户 ID、数量和价格为正、发票号不以 C 开头的明细，构建本次定义的“有效销售”。它服务于特定分析目标，不是所有电商分析都该套用的清洗标准。退货或取消记录，在研究退货行为时仍然有用。

DUCKDB / SQL按公开脚本整理
SELECT
  "InvoiceNo",
  CAST(CAST("CustomerID" AS BIGINT) AS VARCHAR)
    AS "CustomerID",
  "InvoiceDate", "Quantity", "Price", "Country",
  ROUND("Quantity" * "Price", 2) AS "Amount"
FROM ds1
WHERE "CustomerID" IS NOT NULL
  AND "Quantity" > 0
  AND "InvoiceNo" NOT LIKE 'C%'
  AND "Price" > 0;

ds1 表示原始数据集的视图别名；公开脚本运行时按数据集生成别名。筛选条件、列投影与类型转换见复现脚本 ↗。SQL 没有 DISTINCT，也没有调用 drop_duplicates。

01

选择行

按本次销售分析的条件筛选明细。

02

选择字段

保留所需列，不再输出商品编号与描述。

03

派生金额

由数量 × 单价计算 Amount，保留两位小数。

03 / THE MISSING CONTEXT字段也在改变

少了商品信息，
“相同”有了新的含义。

完全重复行检查比较的是当前输出列的整行值。原始数据有商品编号和商品描述，筛选后的结果移除了这两列，并新增金额列：8 列变成 7 列。

机制示意 · 虚构数据始终保留 2 行

只变字段，不删行。

两条虚构商品明细属于同一示例订单，数量与单价相同，但商品码不同。点一下按钮，看看投影后发生什么。

为便于观察，仅展示相关字段；投影时移除商品码、商品说明，并由数量 × 单价派生金额。示意不计入上面的真实体检结果，也不能证明原样例中的重复行都应保留或删除。

原先由 StockCode 或 Description 区分的记录，投影到更少的字段后，可能在全部输出列上变得相同。新增的 Amount 由已有数量和价格计算，也不会补回商品信息。

04 / READ BEFORE YOU REPAIR从评分回到判断

先解释口径，
再判断是否去重。

体检引擎让问题浮出来，业务定义决定怎样处理。这里更有价值的下一步，是沿着原始记录追查三件事：

  1. 01

    分析单位是什么？

    一笔订单、一条商品明细，还是一位客户？先明确一行应该代表什么，再谈重复。

  2. 02

    判重需要哪些字段？

    回到商品信息和原始行，检查当前保留的列是否足以区分不同明细，不能只盯着输出表。

  3. 03

    相同行是怎样产生的？

    投影后相同、重复导入或其他业务原因，需要记录层面的证据。核实之后，再决定保留、合并或删除。

WHAT THIS EXAMPLE SHOWS

评分是判断的起点。
解释数据，才是分析的一部分。

这组记录不证明整体质量已经改善，也不证明工具带来用户提效或商业收益。它说明：评分需要放回具体的数据口径里阅读。
