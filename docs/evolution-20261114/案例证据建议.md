## 01 / Data Helper：最值得升级成完整案例

### 建议放在页面上的文案

> 在一次电商数据预处理中，我没有把“拿到更高体检分数”当作目标。先明确有效销售的筛选口径，再复检结果；即使总分下降，也要解释是哪一项规则、哪一组字段改变了评分。

可以配 3 个事实：**1,067,371 行输入 → 805,549 行筛选结果；缺失单元格 247,389 → 0；规则评分 83.4 → 77.5。**数字下应保留“仓库留存的 UCI Online Retail II 示例结果；本轮未重跑”或等价说明。

### 已有证据

- [案例叙事与 SQL](F:/AICoding/data_helper/examples/ecommerce/README.md)：写明预处理定位、操作、结果与复现命令。
- [输入元信息](F:/AICoding/data_helper/examples/ecommerce/results/00_upload_meta.json:7)：1,067,371 行、8 列。
- [原始体检结果](F:/AICoding/data_helper/examples/ecommerce/results/01_health_check_raw.json:3)：输入行数、重复行与缺失单元格；`quality_score.score` 为 83.4。
- [筛选后的体检结果](F:/AICoding/data_helper/examples/ecommerce/results/02_health_check_clean.json:3)：805,549 行、7 列、缺失单元格 0；`quality_score.score` 为 77.5。
- [复现脚本中的筛选 SQL](F:/AICoding/data_helper/scripts/run_ecommerce_analysis.py:158)：筛选非空 CustomerID、正 Quantity/Price、非 C 开头 InvoiceNo，并选择输出列、计算 Amount。

### 必须解释的口径

1. **前后不是完全相同的列集合。**SQL 移除了 StockCode、Description，新增 Amount，8 列变 7 列。原始记录不同的行，投影后可能显示相同；不能把前后“完全重复行数”直接理解为重复交易增加。
2. 结果中重复惩罚从 1.6 增到 15，影响总分。这能证明通用评分受数据口径影响，**不能证明 314,891 行全部都是合法业务重复**。
3. “筛选为有效销售”是这次分析定义，不是所有电商场景的通用清洗标准。退货/取消记录在退货分析中仍然有价值。
4. 这组结果没有证明用户工作效率提升、商业收益或工具在所有机器上的处理耗时；不写“提效 80%”等数字。

### 本轮公开来源复核与最小事实对象

已实际打开 [公开案例 README](https://github.com/tendernessnick/data-helper/blob/master/examples/ecommerce/README.md)、[原始 JSON](https://raw.githubusercontent.com/tendernessnick/data-helper/master/examples/ecommerce/results/01_health_check_raw.json)、[筛选后 JSON](https://raw.githubusercontent.com/tendernessnick/data-helper/master/examples/ecommerce/results/02_health_check_clean.json)。公开结果与本地留存数值相符。复现脚本依次调用上传接口、执行后端体检、SQL 建新数据集、复检并保存结果，因此应称为“仓库留存的后端实算示例”，不是首页随机生成的交互假数据；本轮未再次执行整条流水线。

[UCI 官方数据页](https://archive.ics.uci.edu/dataset/502/online+retail+ii)确认数据集含 1,067,371 条记录，作者 Daqing Chen，采用 CC BY 4.0。建议页面署名：Chen, D. (2012). Online Retail II [Dataset]. UCI Machine Learning Repository. [DOI:10.24432/C5CG6D](https://doi.org/10.24432/C5CG6D)。不要把该真实公开数据示例写成客户项目。

聚合证据已整理为 [data-helper-case.json](F:/AICoding/my_homepage/site/assets/cases/data-helper-case.json)，只含聚合数、列名、SQL 口径、说明与公开来源，不含交易明细、客户 ID 或本地路径。重复比例 3.22% / 39.09% 是用重复行数除以对应样本量计算，并四舍五入到两位小数；重复扣分 1.6 / 15 是结果文件中存储的规则扣分。前后扣分项有舍入，不用于精确重算总分。

### 能真正落实的页面亮点

在 Data Helper 卡片加一个原生可展开问题：**“为什么清洗后分数反而下降？”**展开后只显示上述 3 个关键数字与 2 句解释，链接到完整记录。它比又一排技术标签更能证明分析判断力。

不要把“83.4 → 77.5”配成绿色向上箭头或称为“质量提升”。可用中性箭头、不同字段数的注记，把这个反常识点讲清楚。

## 02 / Weather Helper：把“可问责的预报”作为工程亮点

### 建议文案

> 预报会更新，出发时的决定不能被事后的新版覆盖。因此我保留开打前看到的预报，再与测站和球友实况对照。工具不仅给建议，也留下判断建议的依据。

### 已有证据

- [项目 README](F:/AICoding/weather_helper/README.md)：57 个公共球场、预报快照冻结、测站/用户双真值、30 天滚动窗口和不足 20 个样本时的处理。
- [快照写入](F:/AICoding/weather_helper/backend/app/services/open_meteo.py:56)：当 `target <= now_hour` 时跳过写入，保留已开始小时的预测版本。
- [提前量副本](F:/AICoding/weather_helper/backend/app/services/open_meteo.py:84)：每个提前量桶只在首次进入时留存；用于比较不同提前量。
- [计分实现](F:/AICoding/weather_helper/backend/app/services/verification.py:164)：分别返回 Open-Meteo / HKO F3 对 station / user 的配对评分。
- [样本状态](F:/AICoding/weather_helper/backend/app/services/verification.py:63) 与 [配置](F:/AICoding/weather_helper/backend/app/config.py:56)：包含 `sufficient_samples`，默认滚动窗口 30 天、最小样本数 20。

### 边界

- 冻结与双轨验证是实现事实，不等于“预报更准确”的测量结果。
- 测站与球友上报各有局限；不称任何一个为每个球场的完美真值。
- 首页 20% / 45% / 85% 是固定示意，不能冒充现场调用出的天气。
- Works 已在本轮换成真实首页截图节选（`weather-current.webp`，2026-11-14 13:09 HKT 静态快照）；这不改变首页固定样例的性质，也不提供准确率或用户收益证据。后续补图重点为球场核心详情、洞察或录屏，无需重做首页。
- 可以设计“出发前 → 到场后”的两步时间线，但没有真实决策记录前，用“机制示意”标签，不编造一次成功避雨故事。

## 03 / NoticeMe：把 AI 放在合适的位置

### 建议文案

> 我希望 AI 帮忙把表达整理成任务，但不把提醒的准时与否交给模型。NoticeMe 把提议、确认、调度拆开：AI 负责建议，人确认后入库，提醒按已保存的规则运行。

### 已有证据

- [AI 设计的三条约束](G:/DSH_Coding/noticeme/docs/TECH_DESIGN-AI.md)：默认关闭、结果预览确认、AI 不进入提醒触发链路；文中耗时是历史说明/预期，本页不新增性能承诺。
- [默认设置](G:/DSH_Coding/noticeme/src/shared/defaults.ts:44)：`aiEnabled: false`。
- [独立 worker](G:/DSH_Coding/noticeme/src/main/ai/manager.ts:158)：通过 Electron `utilityProcess.fork` 运行模型进程，管理队列和卸载。
- [勾选后写入任务](G:/DSH_Coding/noticeme/src/renderer/src/components/QuickAdd.tsx:237)：`addCheckedDrafts` 从建议中选取条目；[按钮入口](G:/DSH_Coding/noticeme/src/renderer/src/components/QuickAdd.tsx:455) 由用户操作触发。
- [提醒调度纯函数](G:/DSH_Coding/noticeme/src/shared/scheduler-core.ts:32)：使用数据库快照、当前时间与补发窗口收集提醒，不调用模型。
- [官方最新发布页](https://github.com/tendernessnick/noticeme/releases/latest)：本轮打开指向 v0.4.3；网站继续以 Windows 已发布说明为准，不因为源码有 macOS 打包命令就宣称双平台包均已发布。

### 边界与表现

- 分层设计不等于“绝不漏提醒”，系统休眠、权限、进程状态仍会影响交付。
- “默认关闭”不等于从未使用网络：启用后可能下载模型。准确表达为“可选本地模型，任务提议在本机处理”。
- 适合展示三步小流程：**一句自然语言 → 可修改的任务提议 → 确认入库**。若用首页虚构样例，不把它标为正在真实调用本地模型。

## 全站内容口径需守住的 7 件事

1. 独立产品 **4 个**；图像去雾是毕业设计/研究，单列。
2. 实习 **5 段，含在岗**；和宏当前正文是职责方向，不新增已完成成果。
3. NoticeMe：源码跨平台架构与当前已发布安装包范围分开描述。
4. 固定天气、匿名邮件、预生成去雾标签保留；真实截图与界面示意分开。
5. 大 CSV 性能可讲实现或具体留存实验，不泛化“百万行秒级”。
6. CPU 在线推理不等于无等待的实时流处理，统一写“CPU 在线推理”更准确。
7. 量化回测是历史研究，不把“跑赢”扩展成投资保证；补图时附期间/基准/费用。

## 截图复评：当前首屏下一步

已观看 `.zcode/home-1440.png` 与 `home-390.png`。暗墨、lime、纸白形成了比旧版更明确的对比，手机的姓名、主张与两个按钮可读，接近一个完整视觉系统。
